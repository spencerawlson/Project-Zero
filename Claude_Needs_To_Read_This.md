**It hangs together.** Clean layered design: pure-logic shared modules (unit-testable, no services) + thin server services that apply them + display-only clients. `default.project.json:1-28` maps `src/shared` → `ReplicatedStorage.Shared`, `src/server` → `ServerScriptService.Server`, `tests` → `ServerStorage.UnitTest`, `src/client` → `StarterPlayerScripts.Client`. Remotes: all `RemoteEvent`, zero `RemoteFunction`s (9 in `ReplicatedStorage.PZ_Remotes`); clients never write game state directly except physics (see below). No TODOs/FIXMEs in the Luau/Lua code.

**Mission M01 "The Awakening" — complete skeleton, playable loop.** Steps (`src/shared/MissionM01.luau:26`): `find_cypher` → `restore_power` → `free_sentinel` → `escape` → `complete`. Objectives: find Cypher (pod P01, west chamber front); restore power — throw breakers B1–B3 **in the console's order** (default `{"B2","B3","B1"}`, `:65`, shuffled per server at `MissionService.luau:152`); free Sentinel (pod P05 release prompt); escape through containment door D03 → service bay → D04 while ZERO locks down. Wiring is genuinely complete: proximity trigger for Cypher (5-stud radius), breaker prompts with lamps + console sequence display, P05 release prompt, exit-zone polling, per-player completion + checkpoint saves on every step change, checkpoint rebuild on rejoin via `worldEffectsFor` (`:109-118`), NPC follow AI (follow 9 studs, catch-up teleport >50, stuck >3 s), HUD objective panel + waypoint markers + queued subtitles. Gaps: **no fail state at all** (only failure is a wrong breaker order resetting the sequence); no timer, no death handling, no combat (by design). Reward is only 150 NEXUS Credits, once — no XP, no item. Two state-machine quirks: on `exited` the shared state never advances to `"complete"` (`MissionM01.luau:101-102` returns `complete_player` but leaves `step == "escape"`), so the server stays in escape/lockdown until every player has finished or a fresh server starts in free-roam; and a mid-mission joiner after the first player finished is dropped into the `escape` step with no way to replay earlier steps in that server.

**Profile / save data — solid, with one naming trap.** Stored (`src/shared/ProfileSchema.luau:17,20-41`, VERSION = 2): `schemaVersion`, `userId`, timestamps, `identity.designation`, `chassis {current, owned, colour}`, `progress {activated, missions, memoryFragments}`, `stats.sessions`, `wallet {credits, rewards}`, `items`, `equipped`, plus v2 additions `status.energy`, `careers.engineering.xp`, `contracts[id]`, `inventory[id→count]`. Datastore is `PZ_Profiles_v1` (`PlayerDataService.luau:15`) — **the name says v1 while the schema is v2**; harmless (just a key namespace) but confusing. Migration is good: fills missing fields from defaults, keeps existing and unknown fields, refuses (throws on) a profile newer than the server — never downgrades. Session locking in `ProfileStore.luau:47-88`: `UpdateAsync` lock with `jobId`, 1800 s stale-lock TTL, save refused after lock loss, key `u_<userId>`. Loads retry 5×, kick if still locked, and fall back to an **in-memory, explicitly unsaved** profile when DataStores are unavailable — that fallback never writes, so it cannot clobber a real save. Autosave every 120 s + save-and-release on leave and `BindToClose`. Wipe/corruption risk: low. Sharp edges: a newer-version profile throws on every load attempt and the player gets a fresh in-memory profile for that session (progress invisible, not destroyed); `PlayerDataService.Update` mutates the live profile table with no validation, so any service bug writes straight into the next autosave; Studio-only dev hook `PZ_DevProfile` (`:142-202`, gated on `RunService:IsStudio()`) can add credits / reset progress — fine as gated, but it is a live-state mutation backdoor in Studio sessions.
